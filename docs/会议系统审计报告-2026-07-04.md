# MeetingOS 会议系统审计报告

> 审计日期：2026-07-04
> 审计方式：只读静态代码审计 + 多子代理并行审计 + 人工复核
> 审计范围：后端、前端、TDuck 集成、公开接口、部署配置、数据库迁移脚本

---

## 1. 审计范围

本次审计对象为 MeetingOS 会议管理系统 monorepo。

技术栈概览：

- 后端：Spring Boot 3 / Java 17 / Spring Security / JWT / JPA / Flyway / MySQL
- 前端：Vue 3 / TypeScript / Vite / Pinia / Naive UI
- 集成：TDuck 表单系统、Nginx、Docker Compose、MySQL、Redis、MinIO

重点审计维度：

- 认证与权限
- TDuck 集成边界
- 匿名公开查询与匿名签到
- 会议状态机与归档语义
- 排座、住宿、晚宴的业务一致性与并发问题
- 日志、Webhook、部署配置
- 前端实时同步和测试覆盖

---

## 2. 总体结论

当前系统已有一些较好的安全和工程基础：

- JWT secret 和 Webhook token 存在启动校验，避免默认弱密钥直接上线。
- 用户管理、系统设置等高权限接口多数有后端权限控制。
- 多数数据库访问使用 JPA 参数化查询，未发现高可信 SQL 注入点。
- 文件导入、CSV 导出、部分日志展示已有脱敏或公式注入防护。
- 签到写入使用参会人行级悲观锁，能防止同一参会人并发重复签到。

但仍存在几类需要优先处理的问题：

1. **TDuck 全局管理员能力被会议管理员间接拿到**，这是最高优先级问题。
2. **匿名公开查询与匿名自助签到默认风险过高**，可被枚举、代签、污染现场数据。
3. **会议状态机可被更新接口绕过**，归档会议也没有真正冻结。
4. **排座、住宿、晚宴存在业务一致性和并发超分问题**。
5. **部分只读/工作人员角色可以看到超出预期的敏感数据**。

建议优先按 P0/P1 顺序修复。

# 3. P0 / 高危问题

## 3.1 TDuck 全局管理员 token 下发给会议管理员，造成跨会议/跨表单越权

### 位置

- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckController.java:73`
- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckService.java:153`
- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckClient.java:233`
- `meetingos-admin/src/views/registration/RegistrationConfigView.vue:721`

### 触发场景

拥有某个会议 `MANAGER` 权限的账号调用：

```http
GET /api/admin/tduck/browser-session?meetingId=<其可管理会议ID>
```

后端只校验该用户能管理这个 MeetingOS 会议，但 `TduckClient.browserSession()` 实际返回的是 TDuck 管理员 token。前端随后把 token 写入同源 `localStorage.token` 和 `localStorage.userInfo`，用于免登录打开 TDuck 编辑器。

### 影响

- 会议级管理员可获得 **TDuck 全局管理员登录态**。
- 可绕过 MeetingOS 的会议级权限，直接访问 `/tduck/` 或 `/tduck-api/` 管理所有 TDuck 表单和报名数据。
- 如果 MeetingOS 同源页面存在 XSS，TDuck 管理员 token 也会因存放在 `localStorage` 中被窃取。
- 这是 MeetingOS 会议权限模型和 TDuck 全局权限模型之间的边界穿透。

### 建议修复

- 不要把 TDuck 全局管理员 token 返回浏览器。
- 后端代理 TDuck 表单操作，并在 MeetingOS 后端逐项校验会议/表单归属。
- 如果必须打开 TDuck 编辑器，应使用 TDuck 支持的单表单、短期、能力受限 token；如果 TDuck 不支持，则该入口至少限制为内置系统管理员。
- TDuck 和 MeetingOS 尽量分离 origin，避免共享 `localStorage`。

## 3.2 TDuck 表单列表/绑定未按会议隔离，会议管理员可枚举或绑定全局表单

### 位置

- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckController.java:58`
- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckClient.java:40`
- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckService.java:73`
- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckService.java:1051`

### 触发场景

`MEETING_ADMIN` 可调用：

```http
GET /api/admin/tduck/forms
```

后端使用 TDuck 管理员 token 拉取 **全局表单列表**，没有按当前会议、当前用户或表单归属过滤。随后用户只要能管理某个会议，就能把任意尚未被 MeetingOS 记录绑定的 TDuck 表单绑定到自己的会议。

### 影响

- 泄露 TDuck 全局表单名称、formKey、发布状态等元数据。
- 可误绑或恶意绑定其他业务已有 TDuck 表单。
- 绑定时会配置 Webhook，可能导致报名数据同步到错误会议，造成串会、数据污染或隐私泄露。
- 和 TDuck 全局管理员 token 下发问题组合后，会议管理员基本拥有 TDuck 全局操作能力。

### 建议修复

- `/tduck/forms` 只返回当前会议可管理、已创建或已授权的表单。
- 绑定时校验 `formKey` 与当前会议的强归属关系，而不是只检查“是否已被其他会议绑定”。
- 全局表单列表、导入既有 TDuck 表单等能力应限制为系统管理员。
- MeetingOS 创建的 TDuck 表单应加 owner/namespace 标记，并在服务端强制校验。

## 3.3 匿名公开查询可通过顺序 meetingId 枚举会议和参会结果

### 位置

- `meetingos-backend/src/main/java/com/meetingos/config/SecurityConfig.java:34`
- `meetingos-backend/src/main/java/com/meetingos/publicapi/PublicController.java:56`
- `meetingos-backend/src/main/java/com/meetingos/publicapi/PublicController.java:94`
- `meetingos-backend/src/main/java/com/meetingos/publicapi/PublicQueryService.java:352`
- `meetingos-backend/src/main/java/com/meetingos/publicapi/PublicQueryService.java:386`
- `meetingos-backend/src/main/resources/application.yml:52`
- `meetingos-backend/src/main/resources/db/migration/V1__init_schema.sql:49`

### 触发场景

匿名用户可调用：

```http
GET /api/public/query-settings?meetingId=1
GET /api/public/query-settings?meetingId=2
POST /api/public/seat-query
POST /api/public/room-query
POST /api/public/dinner-query
```

问题点：

- 公开接口接受顺序数字 `meetingId`。
- `query-settings` 返回会议编号、会议名称、查询字段、匹配模式、结果字段。
- 默认查询字段是 `PHONE,NAME`。
- 默认匹配模式是 `FUZZY`，实现为 `contains`。
- 只要求字段非空，没有最小长度限制。
- 默认 `PUBLIC_QUERY_CAPTCHA_ENABLED=false`。
- 限流是单机内存 IP 限流。

### 影响

- 可枚举会议 ID，泄露会议名称、会议编号、公开查询配置。
- 可用短字符串组合尝试唯一命中参会人。
- 一旦唯一命中，可读取座位、住宿、晚宴等公开结果。
- 默认结果字段包含姓名、座位区域/排号/座号、酒店、房间号、晚宴桌号等。

### 建议修复

- 匿名公开 API 不接受顺序数字 `meetingId`，只接受不可枚举的 public code/token。
- `query-settings` 在会议未公开、查询未开放、状态不合适时不要返回完整配置。
- 默认匹配模式改为 `EXACT`。
- 对 `FUZZY` 设置最小长度、字段组合要求和失败次数限制。
- 手机号查询至少要求完整手机号，或“后四位 + 全名”。
- 默认开启验证码。
- 限流改成 Redis/网关级，并按会议、IP、设备指纹、失败次数组合限流。
- 错误信息尽量统一，减少“未找到/多条/未审核”等枚举 oracle。

## 3.4 匿名自助签到可直接改写签到状态，且默认风险较高

### 位置

- `meetingos-backend/src/main/java/com/meetingos/config/SecurityConfig.java:38`
- `meetingos-backend/src/main/java/com/meetingos/publicapi/PublicController.java:149`
- `meetingos-backend/src/main/java/com/meetingos/publicapi/PublicQueryService.java:127`
- `meetingos-backend/src/main/java/com/meetingos/publicapi/PublicQueryService.java:610`
- `meetingos-backend/src/main/java/com/meetingos/checkin/CheckinService.java:70`
- `meetingos-backend/src/main/resources/db/migration/V1__init_schema.sql:49`

### 触发场景

匿名用户调用：

```http
POST /api/public/checkin
```

只要提供公开查询字段并唯一匹配参会人，后端就会调用 `CheckinService.checkin()`，将该参会人状态改为已签到。

另外，`ensureCheckinSourceOpen()` 信任客户端传入的 `checkinSource`：

- `SELF` 检查 `selfCheckinEnabled`
- `RESULT` 只检查 `checkinEnabled`

因此如果管理员关闭独立自助签到页，但 `checkinEnabled=true`，攻击者仍可构造 `checkinSource=RESULT` 走匿名签到接口。

### 影响

- 知道姓名、手机号等查询字段的人可替别人签到。
- 污染签到统计、现场核验和后续报表。
- 被伪造签到的人现场再签到时会变成重复签到。
- 操作人记录为 `system`，难以追责真实来源。

### 建议修复

- 默认关闭 `selfCheckinEnabled` 和公开签到入口，必须管理员显式开启。
- 不要信任客户端传入的 `checkinSource` 作为权限依据。
- 查询结果页签到应在成功查询后由服务端签发短期、一次性、绑定 `attendeeId/meetingId` 的 nonce，再凭 nonce 签到。
- 独立自助签到应依赖不可猜测的二维码/签名 token，而不是复用姓名/手机号。
- 增加会议状态、签到时间窗口、现场入口、设备或二维码签名校验。
- 默认启用验证码和更严格限流。

## 3.5 会议更新接口可绕过状态机，任意改会议状态

### 位置

- `meetingos-backend/src/main/java/com/meetingos/meeting/MeetingController.java:51`
- `meetingos-backend/src/main/java/com/meetingos/meeting/MeetingService.java:69`
- `meetingos-backend/src/main/java/com/meetingos/meeting/MeetingService.java:149`
- `meetingos-backend/src/main/java/com/meetingos/meeting/MeetingService.java:170`
- `meetingos-backend/src/main/java/com/meetingos/meeting/MeetingRequest.java:29`

### 触发场景

有会议管理权限的用户调用：

```http
PUT /api/admin/meetings/{id}
```

请求体里直接带 `status`，例如：

- `ARCHIVED` 改回 `DRAFT`
- `DRAFT` 直接改成 `IN_PROGRESS`
- `ENDED` 改成 `REGISTRATION_OPEN`

原因是 `update()` 直接调用 `applyRequest()`，而 `applyRequest()` 无条件执行：

```java
meeting.setStatus(request.status() == null ? MeetingStatus.DRAFT : request.status());
```

这绕过了 `transition()` 里的状态流转校验。

### 影响

- 会议状态机失效。
- 归档会议可被恢复。
- 报名、公开查询、签到、归档数据的一致性被破坏。
- 后续依赖状态判断的入口都可能出现异常行为。

### 建议修复

- 更新接口不要接受 `status`，或在 `update()` 中忽略 `request.status()`。
- 状态变更只能走 `transition()`。
- 创建会议时也应限制初始状态，只允许 `DRAFT` 或受控的 `REGISTRATION_OPEN`。
- 增加测试：`PUT /meetings/{id}` 不能绕过状态机。

# 4. P1 / 高优先级问题

## 4.1 归档会议后仍可写入核心业务数据

### 位置

- `meetingos-backend/src/main/java/com/meetingos/meeting/MeetingService.java:86`
- `meetingos-backend/src/main/java/com/meetingos/attendee/AttendeeService.java:73`
- `meetingos-backend/src/main/java/com/meetingos/checkin/CheckinService.java:40`
- `meetingos-backend/src/main/java/com/meetingos/seating/SeatingService.java:190`
- `meetingos-backend/src/main/java/com/meetingos/room/RoomService.java:66`
- `meetingos-backend/src/main/java/com/meetingos/dinner/DinnerService.java:159`

### 触发场景

会议归档后，管理员仍可调用：

- 创建/导入/审核参会人
- 排座
- 分房
- 晚宴安排
- 签到
- 上传/导出部分数据

当前各服务主要校验会议存在和权限，没有统一校验会议是否处于可写状态。

### 影响

- “归档即冻结”的语义失效。
- 历史归档数据继续变化，审计和报表不可信。
- 测试计划中提到“归档会议后普通业务操作受限”，但代码没有完全实现。

### 建议修复

在服务层统一增加会议可写校验，例如：

```java
requireMutableMeeting(meeting)
```

建议规则：

- `ARCHIVED`：禁止全部普通业务写操作。
- `ENDED`：禁止报名、排座、分房、晚宴安排；是否允许补签需单独配置。
- `IN_PROGRESS`：按现场规则允许签到/补报名。
- TDuck Webhook、批量导入、手工创建等入口也要统一校验。

## 4.2 手动排座、分房、晚宴安排未校验参会人审核状态

### 位置

- `meetingos-backend/src/main/java/com/meetingos/seating/SeatingService.java:190`
- `meetingos-backend/src/main/java/com/meetingos/seating/SeatingService.java:335`
- `meetingos-backend/src/main/java/com/meetingos/room/RoomService.java:66`
- `meetingos-backend/src/main/java/com/meetingos/room/RoomService.java:76`
- `meetingos-backend/src/main/java/com/meetingos/dinner/DinnerService.java:159`
- `meetingos-backend/src/main/java/com/meetingos/dinner/DinnerService.java:241`

### 触发场景

对 `PENDING`、`REJECTED`、`CANCELLED` 参会人调用：

```http
POST /api/admin/seating/manual-assign
POST /api/admin/rooms/assign
POST /api/admin/dinner/assign
```

### 影响

- 未审核、已拒绝或已取消人员仍可占用座位、房间、晚宴桌号。
- 后续公开查询和签到会因非 `APPROVED` 被拦截，但资源已经被占用。
- 审核拒绝逻辑又可能因为已分配资源而拒绝改判，形成脏状态。

### 建议修复

在这些入口统一校验：

```java
attendee.getReviewStatus() == ReviewStatus.APPROVED
```

至少包括：

- `SeatingService.ensureAssignable()`
- `RoomService.assignAttendeeToRoom()`
- `DinnerService.upsertAssignment()`

如果业务确实允许“先分配后审核”，需要显式状态模型和回滚策略，而不是静默占用正式资源。

## 4.3 房间容量与晚宴桌容量存在并发超分风险

### 位置

- `meetingos-backend/src/main/java/com/meetingos/room/RoomService.java:85`
- `meetingos-backend/src/main/java/com/meetingos/dinner/DinnerService.java:358`

### 触发场景

两个管理员或导入任务同时把不同参会人分配到同一个剩余 1 个名额的房间/桌号。

当前逻辑是：

1. 两个事务都先 `count` 到未满。
2. 两个事务都写入。
3. 最终超过容量。

### 影响

- 房间或晚宴桌号超过容量。
- 数据库没有容量约束，应用层也没有行级锁或串行化保护。

### 建议修复

- 对目标 `Room` / `DinnerTable` 查询加 `PESSIMISTIC_WRITE`。
- 在同一事务内锁定目标资源后再统计和写入。
- 或引入独立占用表，用唯一键/槽位表达容量。
- 增加并发测试：同一房间/桌剩余 1 个名额时，并发 2 次分配只允许 1 次成功。

## 4.4 手动排座并发冲突会退化为 500，而不是稳定业务错误

### 位置

- `meetingos-backend/src/main/java/com/meetingos/seating/SeatingService.java:190`
- `meetingos-backend/src/main/java/com/meetingos/seating/SeatAssignment.java:17`
- `meetingos-backend/src/main/java/com/meetingos/common/GlobalExceptionHandler.java:51`

### 触发场景

两个请求同时：

- 给不同参会人分配同一个空座位。
- 或给同一参会人分配不同座位。

数据库唯一键：

- `uk_assignment_attendee`
- `uk_assignment_seat`

能兜底防重复，但 `GlobalExceptionHandler` 没有处理 `DataIntegrityViolationException`，最终会走通用异常处理，返回 500 “系统异常”。

### 影响

- 数据最终可能没错，但用户体验不稳定。
- 前端无法明确提示“座位已被占用”。
- 现场操作时并发冲突会表现为系统异常。

### 建议修复

- 给座位/参会人行加悲观锁。
- 或捕获 `DataIntegrityViolationException` 转成 409 业务错误。
- 全局异常处理器增加常见唯一键冲突映射。

## 4.5 管理端候选查询接口以 canView 权限返回原始手机号

## 4.6 操作日志接口后端授权弱于前端策略

### 位置

- `meetingos-backend/src/main/java/com/meetingos/operationlog/OperationLogController.java:21`
- `meetingos-backend/src/main/java/com/meetingos/security/SystemAdminAccess.java:12`

### 触发场景

前端路由看起来要求内置 `admin` 账号才能看日志；`SystemAdminAccess` 也只认用户名 `admin`。但后端日志接口实际是：

```java
@PreAuthorize("hasRole('SUPER_ADMIN')")
```

如果存在非 `admin` 用户但拥有 `SUPER_ADMIN` 角色，可以直接请求：

```http
GET /api/admin/operation-logs
```

### 影响

- 非内置 admin 的超级管理员可读取全局审计日志。
- 日志包含 action、path、参数摘要、IP、异常信息、处理器信息等敏感运维数据。
- 前后端授权策略不一致，容易造成误判。

### 建议修复

如果业务规则确实只允许内置 admin 查看日志，应改为：

```java
@PreAuthorize("@systemAdminAccess.isAdminAccount()")
```

## 4.7 TDuck Webhook 验签前先解析 JSON，验签失败仍持久化 payload

### 位置

- `meetingos-backend/src/main/java/com/meetingos/config/SecurityConfig.java:38`
- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckController.java:141`
- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckService.java:413`
- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckSyncLogService.java:49`
- `deploy/nginx/meetingos.conf:20`

### 触发场景

匿名请求发送到公开放行的 TDuck Webhook：

```http
POST /api/integrations/tduck/webhook
```

当前控制器先：

```java
objectMapper.readValue(rawBody, ...)
```

再进入服务层验签。

验签失败时，服务仍调用失败日志记录，`TduckSyncLogService` 使用 `REQUIRES_NEW`，会把 `data/raw` 写入 `tduck_sync_logs.raw_payload`。

Nginx 全局 `client_max_body_size` 是 50MB。

### 影响

- 未认证请求可以消耗 JSON 解析 CPU/内存。
- 未认证请求可以写入大量失败日志和原始 payload。
- 恶意 payload 长期进入同步日志表，形成日志污染和存储压力。
- 如果未来日志查看/导出链路变化，可能出现二次风险。

### 建议修复

- 先基于原始 body 验证 HMAC/token，再解析 JSON。
- 验签失败不要保存完整 raw payload，只记录最小元数据。
- Webhook 单独设置更小 body 限制和速率限制。
- 优先只支持 HMAC 或专用 header token。
- 移除 query token 兼容模式，或仅允许内网且不记录 query string。
- 给 `tduck_sync_logs` 增加保留期/清理策略。

## 4.8 操作审计 IP 可被客户端伪造

### 位置

- `meetingos-backend/src/main/java/com/meetingos/operationlog/OperationLogService.java:56`
- `deploy/nginx/meetingos.conf:46`

### 触发场景

客户端发送：

```http
X-Forwarded-For: 1.2.3.4
```

Nginx 使用：

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

这会保留客户端原始 XFF 并追加真实 IP。后端直接取第一个：

```java
forwarded.split(",")[0].trim()
```

### 影响

- 攻击者可控制操作日志中的 `clientIp`。
- 影响安全审计、追踪和告警准确性。

### 建议修复

- 边缘代理清除用户传入的 XFF，只写可信真实 IP：

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
```

- 后端只信任来自已知反向代理的转发头。
- 按可信代理链从右向左解析真实客户端 IP。
- 审计 IP 和公开限流 IP 使用同一套可信代理配置。

# 5. P2 / 中优先级问题与稳定性风险

## 5.2 会议时间、报名时间与容量只保存，不做基础业务校验

### 位置

- `meetingos-backend/src/main/java/com/meetingos/meeting/MeetingRequest.java:15`
- `meetingos-backend/src/main/java/com/meetingos/meeting/MeetingService.java:156`

### 触发场景

创建/更新会议时传入：

- `endTime < startTime`
- `registrationEndTime < registrationStartTime`
- `capacity <= 0`
- 已报名人数超过新的 `capacity`

当前代码基本直接保存。

### 影响

- 会议基础数据可进入明显无效状态。
- 公开报名入口只根据开始/结束时间做窗口判断，但没有校验配置本身合理性。
- `capacity` 字段目前也没有在 TDuck 同步、手工创建、批量导入中形成强约束。

### 建议修复

- `endTime` 不得早于 `startTime`。
- `registrationEndTime` 不得早于 `registrationStartTime`。
- `capacity` 必须为正。
- 降低容量时不得低于当前有效报名人数，或保存为警告状态。
- 如果人数上限需要强约束，要在 TDuck Webhook、手工创建、批量导入路径统一校验，并考虑并发锁。

## 5.3 公开查询为全表内存过滤，有性能风险

### 位置

- `meetingos-backend/src/main/java/com/meetingos/publicapi/PublicQueryService.java:352`

当前逻辑：

```java
attendeeRepository.findByMeetingIdOrderByIdAsc(meeting.getId()).stream()
    .filter(...)
```

### 影响

- 每次公开查询都读取会议下全部参会人再内存过滤。
- 1 万级参会人、公开查询高峰时，可能造成数据库和应用内存压力。
- 和默认匿名查询、验证码关闭、单机限流组合后，风险更高。

### 建议修复

- EXACT 查询走数据库索引。
- 手机号、参会码等高选择性字段直接查库。
- FUZZY 查询限制最小长度和字段组合。
- 对公开查询增加缓存、限流、失败熔断。
- 补压测。

## 5.4 Webhook query token 兼容模式容易进入访问日志

### 位置

- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckController.java:141`
- `meetingos-backend/src/main/java/com/meetingos/tduck/TduckClient.java:615`
- `deploy/docker-compose.yml:181`

代码允许：

```http
/api/integrations/tduck/webhook?token=...
```

虽然默认生成逻辑不主动拼 query token，但配置注释允许通过 `MEETINGOS_WEBHOOK_INTERNAL_URL` 显式配置。

### 影响取决于部署

- 如果实际使用 query token，Nginx/代理访问日志通常会记录完整 URI。
- 日志持有者可伪造 TDuck Webhook。
- token 轮换前泄露窗口较长。

### 建议修复

- 移除 query token 支持。
- 统一使用 HMAC 或专用 header。
- 如果必须兼容，仅允许内网，并配置该 location 不记录 query string。
- 对已部署 query token 的环境执行 token 轮换和历史日志排查。

# 7. 需要人工确认的业务/部署边界

## 7.1 TDuck 原始表单地址是否会绕过 MeetingOS 报名窗口

这会让签到人员/住宿人员看到会议详情、统计、公开查询历史等查看类接口。需要业务确认是否符合预期。

- `MANAGER`
- `CHECKIN`
- `ROOM`

# 8. 建议修复优先级

## 8.1 第一优先级：安全边界

1. 禁止向前端返回 TDuck 全局管理员 token。
2. TDuck 表单列表/绑定按会议或 owner 隔离。
3. 匿名公开查询禁止顺序 `meetingId`，默认 EXACT，启用验证码。
4. 匿名签到改为 nonce/token 机制，默认关闭自助签到。
5. Webhook 先验签再解析，失败不保存完整 raw payload。

## 8.2 第二优先级：业务一致性

1. 更新会议时忽略 `status`，状态变更只走状态机。
2. 归档会议统一禁止普通业务写操作。
3. 排座、分房、晚宴只允许 `APPROVED` 参会人。
4. 房间/晚宴桌容量加锁防并发超分。
5. 数据库唯一键冲突映射为 409。

## 8.3 第三优先级：体验与稳定性

1. 签到统计增加轮询或 SSE/WebSocket。
2. 公开查询改为索引查询，避免全表内存过滤。
3. 操作日志 IP 使用可信代理链解析。
4. 补并发测试、归档测试、敏感字段测试。
